# D：踩坑清单

本文件每条都给出适用场景、输入/前提、使用方法（含触发条件与排查步骤）、输出、失效条件、已验证效果、来源失败或观察（含根因）。历史案例只用于避免重复犯错，不改变当前主线。

## 适用场景

当环境、构建、PL 调用或报告出现“看起来成功但结论不可靠”时，按触发条件选条目；不要从头到尾盲执行所有硬件步骤。

## 输入 / 前提

保留首个错误、退出码、工具/模型/工件哈希、实际运行条件和原始日志；涉及设备状态的排查必须先取得对应授权。

## 使用方法

先匹配现象，再做条目中的最小只读检查；每步记录前后证据。不能用重装、刷写、反复下载或扩大测试范围替代根因确认。

## 输出

一份可复核的失败/排除记录：触发条件、已排除原因、根因或仍未知的部分、修复（若有）、验证层级和剩余阻塞。

## 失效条件

不同工具版本、板卡、IP ABI 或运行条件下，历史根因不能直接套用；没有证据的恢复方法只能写模板/未验证。

## 已验证效果

以下条目分别引用本仓库真实历史或当前证据；没有声称第二块板卡、干净环境或他人复现。

## 来源失败或观察

本项目多次把“阶段通过”误读成“系统成功”的风险暴露后，保留失败原文并补充分层门禁。头号案例如下。

### P0：数值正确、时序通过、bit 能下板，但 FFN 端到端更慢（头号案例）

- **适用场景：** 准备把卸载到 PL 的核称为加速器，或想用综合/内核数字代替整机成绩时。
- **输入 / 前提：** 同一模型与输入的 CPU 参考、真实 PL 输出、核/搬运/PS 分项计时、线程与 warmup 条件；保留每次板测原始报告。
- **使用方法：** 触发条件是 PL 数值通过却没有端到端收益。先核对数值覆盖和实际时钟，再按同一条件测 CPU 与 PS+PL 的 P50/P95/P99/max；把核等待、prepare/readback、PS 剩余计算分开，最后判断瓶颈，不先归因于 DDR 或“FPGA 一定快”。
- **输出：** 标记“PL 加速目标失败”的报告、四轮并列数据、瓶颈假设及其证据等级；不删除慢结果，不用静态周期比替代板测。
- **失效条件：** 不同轮次的线程、空转设置、预处理、模型或时钟不同，不能把差异全归因于核；单次 warmup 不能当稳态基线，离线录像吞吐不能当实时控制率。
- **已验证效果：** 历史 FFN 四轮真实板测均慢于 CPU（CPU 约 65–71 ms 量级）：

  | 轮次与日期 | PS+PL 中位耗时 | 同轮 CPU 参考 | 已知范围 |
  |---|---:|---:|---|
  | retry04，2026-10-15 | 2497.4 ms | golden 71.19 ms（唯一一次 warmup，非稳态基准） | 117 帧数值/整数通过；计时条件不完全一致 |
  | r03，约 150 MHz，2026-10-18 | 301.1576 ms | golden 65.5679 ms | 数值通过；150 MHz 不在 100 MHz 签核范围内 |
  | r03，100 MHz，2026-10-18 | 372.2187 ms | golden 64.7386 ms | 117 帧数值通过；正式离线性能仍失败 |
  | r04 v2，2026-10-18 | 170.030144 ms | golden 65.210875 ms | 系统/数值通过；比 golden 慢 2.607 倍 |

  原始证据：开发主源 `pynq_ffn/docs/04_验证记录.md` 第 17、19、20、22 节及对应 `artifacts/`。这些历史 FFN 工件不与当前主线混用。
- **来源失败或观察：** 根因不是“bit 不存在”或“数值错”，而是核有效并行度、PS 剩余计算、准备/读回和串行调度共同形成的端到端成本；静态估计、OOC 时序和内核耗时都不能单独证明加速。后续选择先找有实测贡献的计算段，并保留 CPU INT8 对照。

### P1：设备节点编号漂移，图像或串口接错

- **适用场景：** 重启、插拔或换集线器后设备角色异常。
- **输入 / 前提：** USB 物理拓扑、角色清单和稳定 by-path 链接。
- **使用方法：** 触发条件是旧 `/dev/videoN`/`ttyUSB N` 与角色不一致。依次读 `lsusb -t`、by-path 链接、厂商/产品 ID 和实际身份；按物理口重建映射，禁止按编号猜测。
- **输出：** 带日期的物理口到角色映射和缺失/丢帧记录。
- **失效条件：** 换线、换口或设备固件变化后旧映射失效；仅看到节点存在不代表数据正确。
- **已验证效果：** 2026-10-22 口位配置已核对，仍保留少量丢帧；证据为 `kv260-smartcar-submission/docs/hardware_setup.md`。
- **来源失败或观察：** 根因是 Linux 枚举编号不是持久身份，不是模型输出问题；先修映射再查推理。

### P2：加载目录混入 XSA，PYNQ 误判文件类型

- **适用场景：** bit/HWH 齐全却在 Metadata 或 Overlay 初始化阶段报输入扩展名错误。
- **输入 / 前提：** 实际加载目录文件清单、PYNQ 版本和完整异常。
- **使用方法：** 触发条件是目录同时存在同名 bit 与 XSA。先确认 `is_xsa()` 的判定和实际输入路径；把 XSA 移到追溯目录，只在加载目录保留配套 bit/HWH，再重新做静态身份核对。
- **输出：** 加载目录清单、XSA 追溯位置和新的错误/通过记录。
- **失效条件：** 不同 PYNQ 版本的判定可能不同；移动文件不等于已下载或已验证 PL。
- **已验证效果：** 历史板端 bring-up 按此隔离后完成加载，见 `pynq_ffn/docs/04_验证记录.md` 第 17 节；当前未重新执行该修复。
- **来源失败或观察：** 根因是文件类型探测把 XSA 当输入，不是 bit 数学错误；不要用重复下载掩盖。

### P3：非登录 shell、权限或坏工具壳导致假“核故障”

- **适用场景：** 导入失败、`xclbinutil` 段错误、权限不足或只有 SSH 非登录 shell 出错。
- **输入 / 前提：** 实际解释器、环境变量、用户/组、工具路径和首个异常。
- **使用方法：** 按“解释器/包 → 环境变量 → 工具 `--version` → 设备权限 → 最小运行时”顺序排查；记录每个退出码，不先改核或重装。
- **输出：** 环境差异表、健康工具路径、权限结论和未执行项。
- **失效条件：** 另一台机器或另一用户的 shell 不能复用结论；sudo 票据、PATH 和 XRT 设置不自动继承。
- **已验证效果：** 历史记录定位过非登录 shell 缺环境和工具包装脚本异常，见 `pynq_ffn/docs/04_验证记录.md` 第 17 节；未宣称所有环境均已修复。
- **来源失败或观察：** 根因在运行时环境而非 HLS 数值；先让最小工具调用健康，再进入硬件阶段。

### P4：设计频率与实际 PL 时钟不一致

- **适用场景：** 报告写 100 MHz，但板测性能或周期换算依赖这个假设。
- **输入 / 前提：** 设计约束、HWH 标称值、实际时钟读取和原始分频/PLL 状态。
- **使用方法：** 触发条件是实际读数偏离目标或无法读取。分别在编程/启动前后读时钟，比较约束与实测；不符就停止性能验收。改分频是单独硬件写操作，必须另获授权，不在排查中自动执行。
- **输出：** 实际频率、原始寄存器、约束范围和“可验收/阻塞”结论。
- **失效条件：** 只有 HWH 标称值、旧日志或静态 cycles 时没有实际频率证据；不能用墙钟反推频率。
- **已验证效果：** 历史 r03 记录从 149.9985 MHz 读到 99.999 MHz 的授权复测；当前板测记录 99.999 MHz 且 clock writes=0，见 `kv260-smartcar-submission/metrics/logs/pl_board_run01_report.json`。
- **来源失败或观察：** 根因曾是对分频源和继承状态的未核实假设；时序签核只对指定约束成立，不能覆盖超约束频率。

### P5：缓存、64 位地址或超时处理造成旧数据/不可恢复

- **适用场景：** 输出偶发陈旧、核不 DONE、地址高半部分非零或超时后准备清理缓冲。
- **输入 / 前提：** 本次 register map、设备地址、缓冲生命周期和单调时钟日志。
- **使用方法：** 触发后先停启动；核对低/高地址写法和 alignment，确认“输入 flush → START → DONE → 输出 invalidate”；超时标 hung，保留缓冲和 CTRL，禁止 free/复用/强杀清理，恢复另行授权。
- **输出：** 地址/同步顺序记录、START/DONE/IDLE 计数、hung 状态和处置证据。
- **失效条件：** 不同 PYNQ 缓冲类型或 IP 控制协议不能照搬；超时不等于硬件停止，mock 通过不等于真实恢复通过。
- **已验证效果：** 当前真实 PL 117 帧 0 字节差异、437 次 START 最终 idle，证据为 `kv260-smartcar-submission/metrics/logs/pl_board_run01_report.json`；真实超时恢复未执行。
- **来源失败或观察：** 根因可能是 cache 一致性、ABI 或在途内存生命周期，而非算法误差；先保住内存和证据，再谈恢复。

### P6：把 OOC 或小范围 RTL 当成系统/全量签核

- **适用场景：** 报告出现“PASS”“时序收敛”，准备写成整板完成时。
- **输入 / 前提：** 报告类型、约束清单、外部 I/O delay、事务数、覆盖向量和系统导出记录。
- **使用方法：** 触发条件是只提供单 IP 或冒烟报告。逐项查 OOC/系统、WNS/WHS/TNS、未路由数、外部延时和实际 cosim 事务；缺一项就缩小结论，不补猜。
- **输出：** 分阶段状态表，明确“已验证范围”和“未执行覆盖”。
- **失效条件：** 没有系统约束、外部 I/O 时序或全量输入时，不能称系统签核/完整 RTL；bit 存在也不改变范围。
- **已验证效果：** 当前报告只有 4 事务 RTL，120 帧全量未执行；OOC 缺 122 输入/250 输出外部 delay，证据为 `kv260-smartcar-submission/fpga/report/hls_fixed_acceptance01.json`。
- **来源失败或观察：** 根因是把不同验证层级的“通过”合并；分层报告比一句“全部通过”更可复用。

### P7：用内核 P50、重发循环或最好样本冒充 15 Hz/加速

- **适用场景：** 需要写性能摘要或判断是否达到控制周期时。
- **输入 / 前提：** 同条件 CPU 基线、分项时间戳、输入序号、帧龄、发送序号和持续日志。
- **使用方法：** 触发条件是只报 kernel、瞬时倒数或发送次数。补测预处理/搬运/PS/后处理与端到端，报告 P50/P95/P99/max 和测试时长；分别统计发送、新推理和新鲜输入，不用旧结果重发凑数。
- **输出：** 可持续性能表和“未达到/未执行”的明确结论。
- **失效条件：** 不同线程/精度/平台、排除解码或只测录像时，不能横向宣称整机收益；66.7 ms 预算不是安全延迟保证。
- **已验证效果：** 当前 PS+PL P50 19.6545 ms 仍慢于另一轮 CPU INT8 17.9221 ms；20 秒 300 帧调度不含相机/串口，证据为 `kv260-smartcar-submission/metrics/metrics.csv` 与 `kv260-smartcar-submission/metrics/evidence/car_loop_board_run01.json`。
- **来源失败或观察：** 根因是测量分母和数据新鲜度被混用；先定义“什么算一次有效控制”，再谈频率。

### P8：旧 bit/HWH、模型或清单哈希混入新实验

- **适用场景：** 换核、换参数或从归档目录复现后结果异常。
- **输入 / 前提：** 源文件、配置、bit/HWH/XSA、模型和运行包的 SHA-256 与导出 run。
- **使用方法：** 触发条件是任一哈希或 IP/ABI 不符。停止运行，逐个重算文件哈希，核对同源导出和部署记录；不要手工改 `delivery_manifest.json`，不要拿旧核结果补新核缺口。
- **输出：** 同源工件表、拒绝运行原因和新一轮独立证据目录。
- **失效条件：** 只有文件名相同、时间戳相近或报告写“匹配”而没有实际哈希时，身份仍未证实。
- **已验证效果：** 当前系统工件静态核对和板测钉住哈希，见 `kv260-smartcar-submission/metrics/evidence/system_artifact_verification.json`、`kv260-smartcar-submission/metrics/logs/pl_board_run01_report.json`；独立重建未执行。
- **来源失败或观察：** 根因是归档副本和当前源身份被混用；哈希门禁比文件名和记忆可靠。
