# C：Python 调用 PL 与正确性/性能验收（通用）

## 适用场景

在 PYNQ Python 中通过 AXI-Lite 寄存器启动一个已加载的 PL 核，使用设备缓冲交换数据，并分别验收数值正确性、核耗时和端到端收益。适用于带 `ap_ctrl_hs` 的核；DMA、AXI-Stream 或其他控制协议必须先换成对应接口流程，不能硬套。

## 输入 / 前提

- 已获相应硬件操作授权，Overlay 已按匹配 bit/HWH 加载；本模块阅读本身不执行加载。
- 有本次 HWH/register map、IP 名、控制地址、输入输出形状/dtype、设备地址宽度和参考实现。
- 有可保持存活的连续缓冲区、缓存同步接口、单调时钟计时、超时处置和证据保存位置。
- 有同模型/输入/精度/线程条件的 CPU 基线，以及明确的数值容差或逐字节判据。

## 使用方法

### 1. 启动前核对身份和 CTRL

1. 核对 bit/HWH 哈希、IP 名、物理地址和寄存器表；启动前读 CTRL，确认 IDLE 且没有未完成的 START。
2. 对常见 `ap_ctrl_hs`，CTRL 的 bit0 是 START、bit1 是 DONE、bit2 是 IDLE；位定义以本次导出 HWH 为准，不要把示例位掩码当所有 IP 的标准。
3. 轮询 DONE 时留意“读清除”语义；记录 START 次数、最终 CTRL 和是否正常 close。DONE 只说明核报告完成，不自动证明输出数值正确。

### 2. 写 64 位设备地址

- 使用缓冲区分配器给出的 device address，不是 Python 对象地址或主机虚拟地址；检查对齐、长度和可访问内存范围。
- 64 位指针按 HWH 的低 32 位/高 32 位寄存器分别写入，常见做法是先低后高；实际偏移不能凭经验猜。写完后可按需要回读核对。
- 输入、输出和权重等每个指针都要配对核对；不要把低地址截断后直接启动，也不要把地址解码空间当作实际 RAM 容量。

### 3. 缓存同步顺序不能反

CPU 已写入输入后，先 `flush`（把 CPU 缓存中的新数据推到内存），再写 START；核报告 DONE 后，先 `invalidate`（使 CPU 缓存失效，避免读到旧副本），再读取输出。若输出在启动前也被 CPU 写过，按所用运行时要求处理其同步方向。

推荐顺序：

```text
写输入 → flush(input) → 写地址/START → 等 DONE → invalidate(output) → 读输出
```

`flush` 与 `invalidate` 不是可选的性能开关；漏掉或颠倒可能得到偶发旧数据。具体 API 名称和方向仍以 PYNQ 版本及缓冲类型文档为准。

### 4. 超时先隔离，不立即释放

用 `time.perf_counter()` 等单调时钟设置 deadline，记录最后一次 CTRL。超时只说明软件等待到期，**不证明 AXI master 已停止访问内存**：标记 hung，停止复用/释放/覆盖相关缓冲，保留证据并按经过验证的复位/恢复流程处理；不要自动重试、强制清理或把进程退出当安全恢复。恢复动作需要独立授权。

### 5. 数值与性能分开验收

- 正确性：固定输入、预处理、量化参数、输出形状和参考实现，逐层或逐字节比较；记录样本数、检查字节数、最大误差和未覆盖边界。主机 mock 只能验证软件协议。
- 性能：先 warmup，再分别测预处理、输入复制/flush、核等待、invalidate/读回、反量化、PS 剩余计算、后处理和端到端总耗时。分项 P50 不能机械相加；有重叠时报告时间区间。
- 对照：同一板卡、模型、输入、精度和线程条件下比较 CPU 与 PS+PL；CPU FP32、CPU INT8 和不同轮次分开列，不用平台差异冒充 PL 收益。

### 6. 报告持续率而不是单次倒数

记录样本数、warmup、测试时长、P50/P95/P99/最大耗时或发送间隔，以及持续输出率。控制任务还要分别记录主机发送率、新推理完成率、输入帧龄/时间差、旧结果重发和丢弃数；平均周期约 66.7 ms 只是 15 Hz 预算，不等于传感到执行的安全上限。

## 输出

至少产生两份记录：数值报告（输入/参考/容差/覆盖/差异）和性能报告（分项与总分位数/持续率/条件）。另保存启动次数、最终 idle、超时/hung、缓冲处置和原始日志路径；报告中的每个数字都能回指 JSON 或日志。

## 失效条件

bit/HWH 不匹配、IP 不 idle、地址位宽或偏移猜错、缓冲越界、缓存未同步、DONE 语义误判、超时后复用内存、参考模型不一致或线程条件不同时，结果无效。只测核等待、只测单次最好值、只重发旧结果或只跑录像，不能证明端到端加速、实时新鲜率、串口闭环保留或实车任务成功。

## 来源失败或观察

历史核曾做到数值正确、时序收敛、bit 可下板，却因核计算和 PS/搬运开销导致端到端慢于 CPU；另有时钟假设、缓存顺序、64 位地址和超时缓冲保活的专门检查。由此形成“先证明每一层，再测同一条件端到端；失败就保留并重新定位瓶颈”的方法，不用内核或静态估计数字遮盖系统结果。
