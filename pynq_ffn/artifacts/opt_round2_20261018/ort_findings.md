# ORT 线程池诊断：关闭空转减少了什么

日期：2026-10-18。模型、输入顺序、预处理、输出语义均未改变；本轮只做纯CPU推理，无PYNQ导入、Overlay/PL核/时钟操作、车辆外设或系统维护。

## 结果先说

在同一KV260、ORT1.20.1、预加载同117帧、预热3次、各条件独立进程的实验中，**只关闭会话工作线程的空转，split-ORT中位推理耗时从404.5/411.0ms降到75.2/77.3ms**。两遍使用相反顺序，以减小温度/顺序偏差；所有四输出和整数轮速保持一致。进程线程数同为31，没有通过少开线程来偷换条件。

该实验证明空转是当前多会话实现中一个**主要、可消除的开销**，不证明所有剩余差距均来自线程池，也不证明PS+PL或实时闭环已经加速。

## 做了什么：原路径与新路径

原路径保留9个ORT会话（5个非FFN阶段+4个FFN阶段），每会话4线程。阶段按模型依赖串行推进，但暂时没有任务的其他会话工作线程仍可能忙等，占用4核ARM的CPU调度机会。

实验路径模型和9个会话不变，只设置：

```python
options.add_session_config_entry("session.intra_op.allow_spinning", "0")
options.add_session_config_entry("session.inter_op.allow_spinning", "0")
```

大白话：没有轮到的工人先休息，不要一直绕着机器转；轮到当前阶段时仍可用同样的4线程计算。`ORT_SEQUENTIAL`、`ORT_ENABLE_EXTENDED`、CPUExecutionProvider及原Runtime.run保持。

## 六条件正反序正式结果

均为117帧、预热3次，`run_total_ms`包含原Runtime.run及其FFN诊断张量复制，不含初始化、读盘和预处理；profiling另行运行，未混入下表。

|---|---:|---:|---:|
| 完整CPU图4线程 | 64.793 / 94.923 | 64.624 / 91.636 | 7 |
| 切图全部1线程 | 193.773 / 197.171 | 193.806 / 198.699 | 4 |
| 切图全部4线程、允许空转 | 404.512 / 507.634 | 411.005 / 481.261 | 31 |

切图4线程ON→OFF的中位收益为5.38/5.32倍，CPUtime/墙钟比约3.93→2.70/2.67。非自愿上下文切换约27,000次→738–880次，而自愿切换增加，符合闲置线程休眠而不再持续争用CPU的解释。仅把小图改1线程不如全部4线程关闭空转，说明不是简单“线程越少越好”。

独立profiling中，ON/OFF均观察到9个会话线程池、27个不同worker，算子清单/计数/输入形状相同，调度长尾显著缩短。profiling字段只作辅助，不直接等同空转周期或正式推理时间。

## 生产接口与目标机复验

生产Runtime新增显式可选参数：

```python
runner = Runtime(bundle, mode="split-ort", threads=4, spinning=False)
```

- 省略或`None`：不写两项配置，旧默认保持。
- `False`：显式关闭两类空转；`True`：显式开启。
- 只接受None或真正布尔值，拒绝整数0/1等隐式替代。
- 原模型/ABI/manifest检查、线程默认、执行模式和Runtime.run未变。不实现每阶段线程mapping，不动其他PS/PL驱动。

生产源码SHA为`49ace8fbf61a29e2e54efc174b45477cd08fc5fe469d13547df17326b9745576`，旧冻结实验仍绑定原`023327e...`版本，二者不混用。
